# 一、测试模块脚本说明

## 1.test_actuator_failure_disturbance.py
### PRD（核心业务逻辑）
- **产品目标**：以“可执行测试”方式验证执行器故障扰动在仿真框架中的正确性与可观测性，覆盖三类故障（延迟/部分/完全），在关键时间点采样系统状态并输出日志结论。
- **测试对象与范围**
  - 目标组件：`Upstream_Reservoir`（必有）、`Downstream_Reservoir`（可选）
  - 扰动类型：
    - 延迟故障（control信号延迟生效，3s）
    - 部分故障（效率降至60%）
    - 完全故障（无响应）
- **输入/数据来源**
  - 无外部数据文件；全部由 `SimulationBuilder` 基于场景目录下的 YAML 装配并在内存仿真生成。
- **输出**
  - 日志：添加扰动、活跃时段、关键时刻水位/入流、故障重叠统计、恢复后状态、组件行为变化（mm/m³）
  - 进程退出码：0=成功，1=失败

### 业务流程（文本流程图）
- 加载仿真环境（场景目录 → `SimulationBuilder.load()` → `harness`）
- 校验组件存在性（上/下游水库）
- 依次创建并添加扰动：
  - 延迟故障（上游水库，t=5-15s，delay=3s）
  - 部分故障（下游水库，t=8-18s，efficiency=0.6，若存在）
  - 完全故障（上游水库，t=12-20s）
- 运行仿真循环：
  - 在关键时刻采样：活跃扰动清单、上/下游水位/入流/体积、效率/执行器状态（若有）
- 事后分析与打印：
  - 各故障活跃时间点集合、扰动历史计数、故障重叠样本
  - 故障结束后的恢复状态
  - 组件行为初末对比（水位变化mm、体积变化m³、入流变化）

### 模块与依赖关系
- 顶层函数
  - `load_simulation_harness()`：加载 `harness`
  - `test_delay_failure()` / `test_partial_failure()` / `test_complete_failure()`：构造并注册三类扰动
  - `analyze_component_behavior(component, id, t)`：抽取时刻状态
  - `test_actuator_failure_disturbances()`：编排全流程、仿真步进与结果分析
  - `main()`：异常处理、返回退出码
- 外部依赖（实际使用）
  - `core_lib.io.yaml_loader.SimulationBuilder`
  - `core_lib.disturbances.disturbance_framework`：`DisturbanceConfig`、`DisturbanceType`、`create_disturbance`（内部实例化具体扰动）
  - `logging`、`pathlib.Path`、`yaml`、`numpy`

### 是否使用 core_lib
- 已使用：仿真装配与执行（`SimulationBuilder`/`harness`）、扰动框架（创建并注入三类执行器故障）。

### 数据来源
- 来自场景 YAML 装配后的内存仿真数据（组件状态、扰动历史等）；脚本不读取CSV/DB，所有观测值均由运行时生成。



## 2.test_comprehensive_disturbance.py

### PRD（核心业务逻辑）
- **产品目标**：以可执行测试的方式验证“物理扰动 + 动态扰动 + 网络扰动”的组合效果与相互作用，评估系统物理状态变化、智能体通信负载、扰动叠加强度，并导出结果用于溯源与回归。
- **测试范围**
  - 物理组件（模拟）：上/下游水库、闸门（最简动力学）
  - 智能体（模拟）：ReservoirAgent/GateAgent/CoordinationAgent（带网络扰动属性与消息收发）
  - 扰动类型：
    - 物理扰动：入流变化（INFLOW_CHANGE）
    - 动态扰动：传感器噪声/执行器干扰（动态注册与激活）
    - 网络扰动：消息延迟（延迟+jitter+丢包）、丢包（含突发丢包）

### 业务流程（文本流程图）
- 组合测试（test_physical_and_network_disturbances）
  - 初始化 `EnhancedSimulationHarness`（0-20s, dt=1.0, 启用网络扰动）
  - 加载组件：上游库→闸门→下游库；连线；加载3个模拟智能体；build
  - 添加物理扰动：入流激增（5-13s, target_inflow=150）
  - 添加动态扰动：传感器噪声（3-10s，水位/流量，高斯噪声）
  - 添加网络扰动：延迟（4-12s）与丢包（6-8s，含突发）
  - 运行仿真 → 统计与日志：起末水位/开度、智能体消息发送/接收、扰动活跃状态、导出输出、shutdown
- 相互作用测试（test_disturbance_interaction）
  - 初始化 `EnhancedSimulationHarness`（0-15s, dt=0.5, 启用网络扰动）
  - 加载单一水库与1个模拟智能体；build
  - 同时激活三类扰动：入流（2-12s）、执行器干扰动态（3-8s）、高延迟网络（1-12s）
  - 运行仿真 → 计算
    - 水位变化范围（max-min）
    - 每步活跃扰动数与类型，定位“最大叠加时刻”
    - 通信效率（接收/发送比）
  - 导出输出、shutdown

### 模块与依赖关系
- 核心类/函数
  - `MockReservoir`/`MockGate`：简化物理模型，`step()` 更新水位/流量/开度，`get_state()` 导出状态
  - `MockAgent`：模拟消息感知—决策—执行流程；维护收发记录；支持网络扰动属性
  - `test_physical_and_network_disturbances()`：组合场景全链路执行与统计
  - `test_disturbance_interaction()`：多扰动叠加与相互作用评估
  - `main()`：串联两项测试并输出总结
- 外部依赖（实际使用）
  - `core_lib.core_engine.testing.EnhancedSimulationHarness`
  - `core_lib.disturbances.disturbance_framework`：`InflowDisturbance`、`DisturbanceConfig`、`DisturbanceType`
  - 标准库：`logging`、`time`、`os/sys`、`typing`

### 是否使用 core_lib
- **已使用**：`EnhancedSimulationHarness`（构建/运行/历史/导出/关停）、物理扰动类型与配置框架（`InflowDisturbance`/`DisturbanceConfig`/`DisturbanceType`），以及网络/动态扰动管理接口（add/activate）。

### 数据来源

## @3.test_disturbance_with_harness_fix.py 

### PRD（核心业务逻辑）
- **产品目标**：验证“入流扰动”在仿真中真实生效，绕过 Harness 默认的自动入流覆盖逻辑，确保在扰动时段内上游水库入流被指定值接管，并用理论/实测对比校验效果。
- **关键机制**
  - 通过“给 Harness 打补丁”覆盖 `_step_physical_models`，在扰动活跃时段跳过对目标组件的自动入流计算，仅在非扰动时恢复自动入流。
  - 在固定时窗施加入流阶跃扰动，记录水位/入流时序；以表面积换算理论水位增量，与仿真结果对比验证“扰动未被覆盖”。

### 业务流程（文本流程图）
- 加载场景 → `SimulationBuilder.load()` 得到 `harness`
- 读取 `Upstream_Reservoir` 初始状态（level/volume/inflow）
- 设定扰动计划（开始/持续时间、扰动入流、理论水位变化计算）
- 注入补丁函数覆盖 `harness._step_physical_models`：
  - 若 `active=True` 且组件为 `Upstream_Reservoir` → 不重算入流
  - 否则按拓扑累计上游出流设入流，正常推进
- 用 `dt=0.1s` 手工步进：
  - 扰动时段内设置入流为高值；结束后恢复原值
  - 每秒打印状态（水位变化、入流）
- 还原原方法 → 输出最终水位、对比理论变化 → 判定扰动是否成功

### 模块与依赖关系
- `load_simulation_harness()`：用 `SimulationBuilder` 装配并返回 `harness`
- `patch_harness_for_disturbance(harness, disturbed_component_id, flag)`：
  - 保存原方法 → 定义 `patched_step_physical_models` → 条件跳过入流覆盖 → 回写 `harness._step_physical_models`
  - 返回原方法句柄（用于收尾还原）
- `main()`：组织全流程（初始化→补丁→步进→记录→校验→还原）

### 是否使用 core_lib
- **已使用**：
  - `core_lib.io.yaml_loader.SimulationBuilder`（装配仿真）
  - `core_lib.core_engine.testing.simulation_harness.SimulationHarness`（底层 Harness 类型）
  - `core_lib.physical_objects.reservoir.Reservoir`、`core_lib.physical_objects.gate.Gate`（组件类型）
- 注：未直接实例化上面组件（通过 Builder 加载），核心是对 `harness` 的内部方法打临时代码补丁。

### 数据来源
- **场景 YAML 配置**（由 `SimulationBuilder` 解析装配）；仿真状态数据在内存中生成。
- 无外部CSV/DB输入；仅控制台打印与实时计算（理论水位增量）。


## 4.test_inflow_disturbance.py
### PRD（核心业务逻辑）
- **产品目标**：以“最小可执行用例”验证“入流扰动”对物理计算核心的实际影响，观察上游水库入流与水位随时间的响应，判定扰动是否生效。
- **验证范围**
  - 目标组件：`Upstream_Reservoir`
  - 扰动类型：来水变化（inflow_variation，阶跃型）
  - 观测指标：时间序列上的入流值与水位变化（每2秒采样一次）
- **输出**
  - 控制台打印：初始入流/水位、扰动期间每2秒的“入流/水位”、仿真结束的“最终入流/水位”
  - 判定结果：是否“✅ 入流扰动成功影响了物理计算核心”

### 业务流程（文本流程图）
- 构建仿真：`SimulationBuilder('.') → harness.load()`
- 获取 `Upstream_Reservoir` 初始状态并打印
- 创建 `MessageBus` 与 `DynamicDisturbanceManager`
- 注册入流扰动：
  - 类型 `inflow_variation`，目标 `Upstream_Reservoir`
  - 幅度 `+50 m³/s`，模式 `step`，开始 `t=1s`，持续 `10s`
- 以 `dt=0.5s` 循环 `0→15s`：
  - 每步先 `disturbance_manager.update(current_time, harness)` 再 `harness.step()`
  - 每2秒打印：`入流`、`水位`
- 结束打印最终入流/水位，并以“入流是否不同于默认100.0”判定扰动是否生效

### 模块与依赖关系
- 核心函数
  - `test_inflow_disturbance()`：组装→注册扰动→步进仿真→采样日志→生效判定
- 依赖
  - `core_lib.io.yaml_loader.SimulationBuilder`（装配 `harness`）
  - `dynamic_disturbance_manager.DynamicDisturbanceManager`（动态扰动注册/激活/更新）
  - `core_lib.central_coordination.collaboration.message_bus.MessageBus`（为动态扰动管理提供消息总线）
  - 标准库：`os`、`sys`、`time`

### 是否使用 core_lib
- **已使用**：
  - `SimulationBuilder`（基于场景 YAML 装配仿真）
  - `MessageBus`（消息总线）
  - 与 `harness` 的步进接口协同运行

### 数据来源
- **场景 YAML 配置与运行期内存数据**：
  - 组件/拓扑由 `SimulationBuilder` 从场景目录解析装配
  - 入流、水位时间序列由仿真运行时生成；脚本不读取外部 CSV/DB 文件。

## 2.advanced_adaptive_identification.py
### 核心业务逻辑

- **产品目标**: 评估并对比多种参数辨识算法（RLS/Kalman/PSO/混合）在“精度与收敛速度”的综合表现，生成可视化与报告，用于指导算法选型与参数配置。
- **业务范围**
  - 算法对象：参数辨识器（2维参数：积分系数、时滞系数）。
  - 评估维度：总体评分、精度评分、收敛时间、最终误差；并提供渠道（Channel）维度对比与排名。
- **输入**
  - 无外部数据依赖；由脚本内部生成仿真测量数据（含多频激励与高斯噪声）。
  - 固定测试集：`Channel_1/2/3` 的真实参数集。
- **输出**
  - 可视化：`experiment_results/advanced_identification_comparison.png`
  - 指标JSON：`experiment_results/advanced_identification_metrics.json`
  - 报告JSON：`experiment_results/advanced_identification_report.json`
  - 报告Markdown：`experiment_results/advanced_identification_report.md`
  - 终端摘要：最佳算法、平均评分、改进等级
- **关键指标与算法策略**
  - 评分体系（多目标权重）：`total_score = 0.7*accuracy + 0.3*speed`
    - **accuracy_score**: `1/(1+final_error)`
    - **speed_score**: `1/(1+convergence_time/100)`
    - **final_error**: `||estimated_params - true_params||`
    - **convergence_time**: 误差<0.05 且步数>50 时的迭代步；否则记 `max_iterations`
  - 算法机制
    - **RLS**：递推最小二乘，遗忘因子与协方差更新
    - **Kalman**：简化状态估计（单位转移、单位观测）
    - **PSO**：粒子群全局搜索（位置/速度更新、边界约束）
    - **混合**：RLS/Kalman/PSO 加权融合（可自适应微调）
  - 收敛与自适应：若性能改善停滞，动态下调RLS遗忘因子、增大Kalman过程噪声、调整PSO参数（降低惯性、提升个体学习因子）

### 业务流程（文本流程图）

- 启动主流程
  - 生成3个渠道的真实参数集
  - 对每种算法（RLS/Kalman/PSO/混合），逐渠道执行“评估”
    - 循环生成仿真测量数据（带噪声）
    - 调用辨识器更新参数（按各算法/混合策略）
    - 记录参数轨迹、误差轨迹，判断收敛
  - 汇总各渠道×算法结果 → 计算统计指标（均值/方差/最佳最差）
  - 生成图表：评分对比、精度评分、收敛时间、参数收敛、误差收敛、算法排名
  - 产出报告（JSON/MD）：最佳算法、算法排名、各渠道最佳方案、改进建议
  - 保存所有文件至 `experiment_results` 目录并打印摘要

### 模块与依赖关系

- **类 `AdvancedAdaptiveIdentifier`（辨识核心）**
  - 配置：RLS/Kalman/PSO/混合 权重与超参
  - `update_parameters(measurement_data, control_input)`：按 `method` 更新参数
    - `rls_update(phi, y)`：参数与协方差递推

## 23.integration_performance_validator.py
### PRD（还原自 23.integration_performance_validator.py 的产品业务逻辑）

- 核心目标
  - 验证“分布式数字孪生仿真系统”的集成与性能，包括：组件与智能体集成、扰动集成、压力/并发/内存泄漏/稳定性测试，并输出报告。

- 范围边界
  - 仅围绕仿真框架的可用性与性能验证；不涉及真实生产控制逻辑、外部数据对接与真实消息总线联调（消息总线测试为占位/简化）。

- 成功标准
  - 各项测试执行不抛异常、仿真可运行并产生步骤历史；压力与并发测试在合理时间内完成；稳定性测试能完成大部分步数；内存增长在阈值内；最终整体状态标记为 passed（当前代码固定返回 passed）。

- 关键测试项与判定逻辑（核心业务逻辑）
  1) 基础集成验证
     - 组件集成：构建 `Reservoir`、`Gate`，添加 `MockAgent`，运行仿真，验证 `harness.history` 有步数。
     - 智能体集成：添加多个 `MockAgent`，运行后累加 `agent.step_count` > 0。
     - 扰动集成：对 `Reservoir` 注入入流扰动、传感器噪声扰动，运行后检查 `disturbance_manager.get_disturbance_history()` 数量 > 0。
     - 消息总线集成：返回固定可用标志（占位，未做真实收发校验）。
  2) 压力测试
     - 高频仿真：`dt=0.1`、`duration=50`，要求 `simulation_steps > 400`，记录执行时长与步速。
     - 大规模组件：一次性添加约 10 个组件（库/闸混合），要求在 30 秒内完成，且有步数。
     - 密集扰动：对库/闸注入多次入流、传感器噪声、执行器故障，要求 `simulation_steps > 50`。
     - 附带系统监控：采样 CPU%、内存占用率、已用/可用内存（0.5s 间隔），出测试报告。
  3) 并发性能测试
     - 线程池并发跑 3 个仿真实例（各自含 `Reservoir` 与 `MockAgent`），统计成功/失败次数与各自时长、步数。
  4) 内存泄漏测试
     - 连续执行 5 次短仿真，强制 GC；比较初末内存（MB），若增加 > 100MB 判定为可能泄漏。
  5) 稳定性测试
     - 长时运行（`end_time=100, dt=1.0`），记录系统监控（2s 间隔）；要求完成步数 > 90；结束后关闭仿真。
  6) 报告与汇总
     - 汇总各测试结果、总耗时、时间戳、整体状态；写入 `integration_performance_output/*.json`；打印摘要。

- 输入与输出
  - 输入：各测试内置 `config`（开始/结束时间、步长、是否启用网络扰动=false）、组件参数、扰动参数（入流目标、噪声水平、执行器故障类型等）。
  - 输出：控制台日志、汇总 JSON 报告文件、系统性能监控摘要。

- 性能与资源指标
  - 关注 CPU 使用率、内存占用率/MB、步数、执行耗时、步/秒。
  - 内存增长阈值：>100MB 视为可能泄漏。

- 失败与恢复
  - 单项测试异常不影响其它测试继续；各测试返回状态与错误信息；监控在异常时也会被停止与清理。

## 24.network_disturbance.py
### PRD（核心业务逻辑）

- **产品目标**：在数字孪生/分布式仿真中注入网络层扰动（延迟、抖包、丢包），用于验证系统在不可靠网络下的鲁棒性与性能。
- **对象与范围**：
  - 扰动类型：`网络延迟扰动（支持固定/随机/渐变）`、`数据包丢失扰动（含突发丢包）`
  - 作用域：基于消息总线的主题（topics）与代理（agents）选择性生效
- **核心流程**：
  1. 创建扰动实例（由管理器）并完成参数配置
  2. 指定开始时间与持续时长激活扰动（调用消息总线启用网络扰动）
  3. 运行期定时更新：按模式动态调整延迟或按概率触发突发丢包
  4. 到时自动停用（调用消息总线停用网络扰动）
  5. 可随时查询所有扰动与消息总线状态；支持管理器统一关闭

- **功能要点**：
  - 网络延迟扰动 `NetworkDelayDisturbance`
    - 参数：`base_delay`（ms）、`jitter`（ms）、`packet_loss`（概率）、`affected_topics`、`affected_agents`、`delay_mode`（`fixed`/`random`/`gradual`）
    - 运行期：
      - `fixed`：恒定基础延迟
      - `random`：每次更新将基础延迟按50%~150%随机倍增
      - `gradual`：按时间进度在0→峰值→0间线性变化
    - 实施方式：通过消息总线的 `enable_network_disturbance` 与动态写入 `network_disturbance.base_delay`
  - 数据包丢失扰动 `PacketLossDisturbance`
    - 参数：`packet_loss_rate`、`burst_loss_probability`、`burst_loss_duration`、`affected_topics`、`affected_agents`
    - 运行期：以设定概率触发“突发丢包”，临时将 `packet_loss_rate` 提高为原来的5倍（上限0.9），并在`burst_loss_duration`后恢复
    - 实施方式：通过消息总线配置基础丢包率并在突发窗口内临时提高

- **管理与可观测性**：
  - 管理器 `NetworkDisturbanceManager`
    - 创建/激活/更新/停用/关闭扰动
    - 维护 `active_disturbances` 与 `disturbance_history`
    - 汇总查询接口：返回所有扰动状态与消息总线网络扰动状态

- **`NetworkDisturbanceManager`**

  - 管理对象：`NetworkDelayDisturbance`、`PacketLossDisturbance`

## 38.time_series_analysis.py
### PRD（核心业务逻辑）
- **产品目标**：对 Rule 与 MPC 两种模式在各场景下的扰动—响应—指令进行“按被控对象（Gate_1/2/3）”的时间序列深度分析，输出交互可视化与分析报告，支撑控制策略评审与结论固化。
- **分析维度**
  - 扰动输入：降雨入流、用水需求（按闸门关联渠道映射）
  - 响应：上游水位（含目标水位对比、RMSE/统计）
  - 控制指令：本地（现地）设定点 vs 中央MPC设定点（平滑度、变化率、控制频率）
- **输入/数据来源**
  - 来自已有仿真输出 CSV：`./experiment_results/{mode}_{scenario}_data.csv`
  - 模式：`rule`、`mpc`；默认场景：`normal_operation`、`rainfall_disturbance`、`extreme_disturbance`
- **输出**
  - 交互可视化（HTML）：`./experiment_results/time_series_analysis/{Gate}_{scenario}_comprehensive_analysis.html`
  - 场景分析报告（MD）：`./experiment_results/time_series_analysis/{scenario}_time_series_analysis_report.md`

  - 汇编场景报告（结论与对比：平滑度提升%、控制频率变化%等）
